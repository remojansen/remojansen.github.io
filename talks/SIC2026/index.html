We Optimized for Speed

For years, standard developer experience focused entirely on removing friction to ship as fast as possible, even when the long-term benefits were sacrificed:

  • Dynamic types took over static types: We moved from C++/Java to JavaScript/Python. Compilation that verified correctness across the entire application was seen as friction. Even when complexity forced us to retrofit type systems (TypeScript, Python type hints), they remained optional, structural, and with no runtime guarantees — the dynamic foundation stayed.
  • NoSQL exploded: We moved from SQL to NoSQL. Predefined schemas and database-enforced constraints were seen as rigidity slowing teams down.
  • Explicit architectures stayed niche: Whether it was Haskell's explicit effects, the actor model for distributed computing, or architectures like hexagonal (AKA ports and adapters, SOLID, onion) — anything that demanded upfront design discipline failed to become mainstream at the expense of speed.

This absolute removal of friction "made sense" when writing code was the primary human bottleneck.

AI Flips the Equation

Generative models can synthesize massive blocks of software near-instantaneously. However, this flips our developmental bottlenecks upside down.

Phase Traditional Era (Before AI) AI-Assisted Era (Now)
Writing Code Expensive, slow, constrained by physical key inputs Virtually free, instantaneous
Verification Manageable; author reviews localized logic mappings Extremely expensive, cognitively taxing

The core engineering roadblock has shifted from generating output to verifying correctness. Optimizing for speed of writing no longer makes sense — we now need to optimize for speed of verification.

Rigidity is No Longer Friction

In the age of AI, rigidity is no longer inherently friction. When a system's constraints are implicit, they generate friction — AI can't see them, humans can't verify them. But when constraints are explicit, they become a lubricant — enabling faster verification, clearer generation, and safer iteration. The axis that matters is no longer Rigidity vs. Flexibility but Implicit vs. Explicit.

Implicit Systems

  • Cannot be formally verified — correctness depends on runtime observation.
  • No data integrity guarantees — constraints are assumed, not enforced.
  • Code patterns built on inference & runtime conventions.
  • Bugs are discovered downstream at runtime.
  • Logic relies heavily on tribal developer memory.

Explicit Systems

  • Can be formally verified — correctness is provable before execution.
  • Data integrity is enforced at the system boundary — constraints are declared and guaranteed.
  • Express and enforce structures directly inside code syntax.
  • Capture failures instantly with compile-time assertions.
  • Establish static, machine-readable validation contracts.

Implicit = Hidden Intent

JavaScript + MongoDB + Promises 
// No schema, no constraints, no effect tracking
async function createOrder(userId, product, status) {
  await db.collection('orders').insertOne({
    userId,          // AI: what type? what table? does it reference anything?
    product,
    status,          // AI: what values are valid? has to guess from usage
    createdAt: new Date()
  });
  await notifyWarehouse(product); // AI: is this required? what if it fails?
}

Intent is Hidden

AI must infer everything from patterns — hallucinations are inevitable.

  • AI Blind Spots: No types, no schema, no declared effects — AI is forced to guess relationships, valid values, and side effects.
  • Review Drag: Pull requests require manual tracing or runtime sandbox runs to verify validity.

Explicit = Encoded Intent

TypeScript + PostgreSQL + IO 
type OrderStatus = 'pending' | 'shipped' | 'delivered'; // AI: exact valid values

type CreateOrder = {
  userId: string;       // AI: FK → users.id, knows the relationship
  product: string;
  status: OrderStatus;  // AI: constrained set, will never generate "shiped"
};

function createOrder(order: CreateOrder): IO<Result<Order, ConstraintError>> {
  return pipe(
    query('INSERT INTO orders (user_id, product, status) VALUES ($1, $2, $3)',
      [order.userId, order.product, order.status]),
    flatMap(o => notifyWarehouse(o.product).map(() => o)) // AI: error handling enforced by compiler
  );
}

Intent is Encoded

AI reads types and constraints directly — no inference needed, no hallucination.

  • AI Blueprint: Types, enums, and FK relationships give AI a complete context map — generation is accurate on the first attempt.
  • Layered Verification: Compiler catches type errors, DB enforces enums and foreign keys, IO declares side effects. Errors are impossible to miss.

Better Output, Faster Verification

Explicit constraints accelerate AI-assisted development on two levels:

1. Richer AI Context

  • Types, schemas, and contracts act as a compressed blueprint of your system's intent.
  • AI doesn't need to guess relationships, valid values, or boundaries — they're declared.
  • The more you formally encode up front, the fewer hallucinations and the more accurate the generated code.

2. Layered Verification

  • Each explicit constraint adds a verification layer: compiler → database → contracts → effect system.
  • AI-generated code passes through multiple automated checkpoints before reaching production.
  • More layers = more confidence in correctness without human review for every line.

Constraints don't slow you down — they compress the verification loop from hours of manual review to seconds of automated checks.

The DX Paradox

The exact fluid design setups we chose to make human typing fast now create extreme drag for AI-assisted workflows:

  • Dynamic types: AI has no blueprint of your system — it guesses signatures, invents properties, and generates code that looks correct but breaks at runtime. Every output requires manual verification.
  • Schema-less databases: Without declared relationships and constraints, AI generates queries against assumed structures. No FK, no enums — data corruption happens silently.
  • No explicit side effects: Without explicit side effects, we can't be sure AI handles them correctly — making human code review inevitable.
  • No concurrency model: Without explicit boundaries for parallel computation (like the actor model), AI generates code with shared mutable state, race conditions, and deadlocks.
  • No architecture tests: Without tests enforcing structural boundaries and dependency rules, AI crosses layers, imports forbidden modules, and breaks architectural intent — while unit tests still pass.
  • No explicit memory ownership: Without ownership rules (like Rust's borrow checker), AI generates memory leaks and use-after-free bugs that only surface in production.

Two Audiences Now

Our code syntax is no longer written purely to be compiled down for local servers; it has two readers:

1. Human Engineers

Need semantic code layouts and clear logical separation to parse complex software modules and safely review pull requests.

  • Can a human review and comfortably extend this code?
  • Are boundaries and responsibilities clear at a glance?
  • Is the cognitive load manageable during code review?

2. AI Agents

Require clear interfaces, complete types, and schema boundaries to execute stable, hallucination-free edits.

  • Is the contract explicit enough for compilers to auto-verify?
  • Can AI read the full intent without guessing?
  • Are constraints machine-readable, not just human-readable?

Being an LLM is hard

You write code once, you read it a hundred times. We've all felt the pain of returning to our own code months later and thinking "who wrote this?" Well, for an LLM — every single prompt is their first day at a new company. No onboarding, no tribal knowledge, no memory. Just whatever context is in the repo.

What Rises in Value

As the costs of writing code fall toward zero, architectures, tools, languages, and patterns that prioritize easy, machine-executable verification are surging in value.

Flexibility-First (Slow AI Verification) Explicitness-First (Fast AI Verification)
Schema-less Document Databases (NoSQL) Database Enforced Constraints (SQL)
Dynamic Types (JS / Python) Static Types (TS / Rust / Go)
Loosely-typed APIs (REST) Type Safe Contracts (Protobuf / gRPC)
Implicit, undocumented side effects Explicit, Declaratively Modeled Effects (FP)
Untracked Memory Management (C/C++) Explicit Memory Ownership (Rust)
Shared State Concurrency (Threads/Locks) Explicit Message Passing (Actor Model)
External Documentation (Confluence / Wikis) In-Repo Documentation (Markdown / ADRs)

We must optimize for richer AI context and faster automated verification.

Good Friction vs. Bad Friction

Not all friction is equal. Some slows you down and invites AI to hallucinate. Some catches mistakes before your users do.

Bad Friction (Eliminate)

  • Flaky unit tests that cry wolf until everyone ignores them
  • Stateful distributed systems nobody can reason about
  • Unpredictable side effects hidden deep in the call stack
  • Shared mutable state across service boundaries

Good Friction (Adopt)

  • Type errors that catch null references before production
  • Foreign keys that make invalid states unrepresentable
  • Type-safe protocols (protobuf) that catch breaking changes at compile time
  • Ownership rules that prevent memory leaks at compile time
  • Effect systems that make side effects visible in the type signature

Predictions

If AI models reach a plateau, tools and practices that encode verification through explicitness will rise in popularity:

  • Static types become non-negotiable — TypeScript already won JavaScript. Python type hints and validated configs are next.
  • Effect systems go mainstream — Side effects tracked in the type signature, not buried in runtime surprises.
  • Schema-first protocols replace documentation — Protobuf, GraphQL schemas, and OpenAPI as the single source of truth.
  • NoSQL takes a hit — Foreign keys and constraints win over "flexible" document stores with no guarantees.
  • Architecture tests replace architecture diagrams — Executable rules, not Confluence pages nobody reads.
  • Explicit architecture patterns gain adoption (e.g. Actor Model, Hexagonal Architecture) — Replacing "best practices" wikis with enforceable structure.
