Context

Why Manufacturing Ideas Still Matter

Software has borrowed a surprising amount from manufacturing. Some of the most influential ideas trace back to Toyota:

  • Lean Software Development & Kanban
  • Limiting work in progress & reducing waste
  • Optimizing flow, continuous improvement & pull systems

JIDOKA

Automation with a human touch: when an abnormality is detected, the process stops rather than continuing to produce defects.

JUST-IN-TIME

Produce what is needed, when needed, in the amount needed — matching production to actual demand.

The Shift

The Software Bottleneck Is Moving

For most of software history, the constraint was production capacity — humans writing, reviewing, and testing code. We addressed this via:

  • IDEs for faster navigation & writing
  • Expressive languages & frameworks
  • Automated CI build & test pipelines
  • Agile & Kanban for flow

Enter AI Coding Agents

An agent can read a codebase, modify dozens of files, run commands, and iterate without waiting for human typing speed.

Production capacity skyrockets. The new bottleneck is Verification.

Core Questions

Looking at the Factory Floor Again

Software has no physical assembly line, but the underlying challenges are identical. We must ask:

01. How do you prevent defects?
02. How do you detect problems as early as possible?
03. What should happen when an abnormality occurs?
04. How much unfinished work should be allowed to accumulate?
05. How do you improve the process rather than inspect output?
06. How do you speed up without letting defects escape?

Automation with a Human Touch

Jidoka & The Software Andon Cord

If a machine detects an abnormality, it stops. Build quality directly into the process rather than inspecting at the end.

A Jidoka-inspired agent is designed to stop within clear constraints—not to keep retrying while unverified state accumulates.

Control Mechanisms

Every Invariant Can Be an Andon Cord

An Andon signal isn't just a passive dashboard warning; it's an active control mechanism where the agent loses permission to proceed until fixed.

  • Type error that would crash the program ➔ Compile / type-check fails
  • Broken interface between services ➔ Contract test fails
  • Security rule violated ➔ Policy engine blocks
  • Database change destroying data ➔ Migration safety check stops agent
  • Drop in test coverage or performance budget exceeded

Fail-Safe Design

Poka-yoke — Mistake-Proofing the Environment

We tend to ask: “How can we detect whether the agent made a mistake?”

A far better question: “Can we make it impossible for the agent to make this particular mistake?”

CORE DESIGN PRINCIPLE

Don’t teach the agent not to make a mistake when you can design the system so the mistake cannot be made.

The same fail-safe boundary can protect dependencies, secrets, migrations, and permissions.

Tiered Verification Pipeline

The Economics of Inspection

Catch cheap defects cheaply through a tiered inspection pipeline before invoking slow, expensive verifications.

An agent inserting a simple syntax error should be blocked in seconds by the first layer, not via a 45-minute E2E test suite.

Conclusion

The Quality System Is the Deliverable

A mediocre agent operating inside an exceptional verification environment will consistently outperform a brilliant agent operating inside a weak one.

  • Mistakes must be cheap — Caught early, contained, inexpensive to fix.
  • Mistakes must be visible — Andon signals that stop the process, not silent dashboards.
  • Mistakes must be corrected quickly — Root-cause learning that permanently updates constraints.
